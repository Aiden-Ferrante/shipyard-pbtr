# v0.31.1 — A sub-problem can cut its own version

Light cycle plan under [[0.) Development Protocol 1.0]]
Opened 2026-08-26

Addresses **A sub-problem can cut its own version**

> Opening a cycle against a leaf beneath a project node succeeds and scaffolds a
> Light cycle record, and the version it proposes is a PATCH — so the weight the tree
> reports and the weight the number reports agree without anyone choosing.

## Problem

`nearest_repos()` searched downward only. A problem carrying a repo answered for
itself; a goal above the project layer inherited from the nearest repo below it; and
nothing looked up. Since `_repo_owner` gives a repo to exactly one problem, the repo
sits on the project node, and every sub-problem beneath it was refused:

```
POST /api/problems/<leaf>/cycles/open
→ 422 "no repo beneath this problem — a cycle cuts a version in a repo,
       and there is none to cut"
```

The refusal was not the cost. **The workaround was.** Four cycles in a row were
opened against the project node instead, and by v0.31.0 that had started moving the
version numbers: a light cycle's worth of work was cut as a MINOR because only a
branch node could hold a cycle. The chart's shape was choosing the weight, which is
backwards — `repo._weight()` and `chart.role()` are meant to agree because work has
a size, not because of where a repo happens to sit.

That also means the intended workflow — a project has its own problem chart, and its
sub-problems lead into cycles — could not be run at all.

## Appetite

One sitting. One fallback and its tests.

## Plan

`nearest_repos()` gains an upward fallback, consulted **only when the downward walk
finds nothing**: the nearest ancestor carrying a repo, breadth-first, stopping at the
first generation that has one.

**Non-goals.** No change to `_repo_owner` — one repo still belongs to one problem.
No change to what a goal offers: composition is the downward answer and it keeps
winning.

## Exit criteria

A leaf beneath a project opens a Light cycle and proposes a PATCH; a goal still
offers what it decomposes into; a sibling of a project inherits nothing from it.
`make test` and `make check` green.

## Build

`_repo_above()` beside `nearest_repos`, and one changed return: `found or
_repo_above(con, pid)`. Downward wins whenever it finds anything, so a goal is never
offered the tag of a bearing above it — that would put a parent's release in the
picker for its own children, which is the composition read backwards in the other
direction.

**Upward walks only your own ancestry.** A sibling of a project is not part of it: a
leaf beside `stocklake` under the same bearing gets nothing, because the bearing's
repo is something it found by looking *down* at its other child. Tested explicitly,
since this is the case where a too-eager fallback would let abstract work cut a tag
in a line nobody meant to touch.

**It was blocked on a gate that turned out to be its own precondition.** The reason
recorded in `Backlog.md` for not fixing this earlier was that siblings inheriting one
repo would each propose the same next version. `_open_gate`, shipped in v0.29.1,
refuses a second open cycle per repo — so the collision cannot happen. And
`versions_claimed_in()` now resolves *more* problems to each repo rather than fewer,
so `next_version` sees more claimed numbers and gets more careful, not less. The fix
was waiting on something that had already shipped two cycles earlier.

**This cycle bootstrapped itself.** The fix was written first, and then its own cycle
was opened against its own leaf — the first cycle in this repo's history opened
against a sub-problem. The scaffold says `Light cycle` and the route proposed
`v0.31.1` without being told.

## Test

`make test` — **445 backend + 5 frontend, green** (438 before; five chart tests and
two gate tests added). `make check` clean.

**Negative test, run rather than assumed.** With `or _repo_above(...)` removed, two
tests go red — `test_a_sub_problem_inherits_the_project_above_it` and
`test_inheritance_stops_at_the_nearest_ancestor`. The other three new chart tests
pass either way, correctly: they assert what must **not** change (downward still
wins, a sibling inherits nothing, an abstract leaf still offers nothing), and a guard
test that fails when the guard is removed would be testing the wrong thing.

**End to end, in `test_gate.py`:** a leaf reports `role=leaf`, `bump=patch`, proposes
`v2.0.1` against a `v2.0.0` fixture, opens, and writes a record containing
`Light cycle`. And the collision case the backlog worried about, asserted directly:
two sub-problems sharing an inherited repo, the second refused with *"already has a
cycle open"*.

**Driven in the served app** at :8847, with :8845 untouched. `No cycle opens on
undirected work` — a leaf of the Directed work arc, which could not have held a cycle
this morning — reports `role: leaf | bump: patch | proposed: v0.31.2`, and its "link
a cycle" picker now lists shipyard's real tags where it had nothing to offer before.
No console errors.

**One mistake worth recording.** The first draft of the chart tests reused repo names
already taken elsewhere in the suite, and `_repo_owner` refused them — the invariant
merged at the start of the arc catching a test that violated it. Fixing it, a blanket
string replace also renamed a *pre-existing* test's repo; caught by diffing the file
for deletions rather than by the suite, which stayed green either way. A rename that
passes is the kind that ships.

## Review

**The fix is one line and the cycle was worth running for the two paragraphs above
it.** `found or _repo_above(con, pid)` is the whole change. Everything else is
stating which direction wins and why, and proving the three things that must not
move.

**A blocker recorded twice is a blocker with data.** This went into `Backlog.md`
after v0.30.0 with a reason not to fix it, hit again in v0.31.0, and the second hit
carried the evidence the first lacked — it moved a version number. Writing down the
reason for *not* doing something is what made the second encounter decisive rather
than merely annoying.

**The stated risk had already been retired and nobody noticed.** The backlog entry
said inheritance was unsafe because of version collisions; the gate that prevents
them shipped in the same arc, one cycle before the entry was written. A deferred
item's blocker deserves re-reading when it comes up, because the codebase moves
underneath it.

**What carries forward.** The version-number distortion in v0.31.0 stands — it is
tagged and the changelog says why. Nothing is being rewritten to hide it. Future
cycles on sub-problems cut PATCHes as they should.
