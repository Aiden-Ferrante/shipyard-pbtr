# v0.35.0 — A destructive write proves it read its impact

Light cycle plan under [[0.) Development Protocol 1.0]]
Opened 2026-09-04

Addresses **A destructive write proves it read its impact**

> The five destructive routes (shipyard delete problem, thaw; MC stop app, delete model; learnhub delete course) refuse without a token their impact read issued.

## Problem

Every impact read in the fleet ended with "read before the button, never after" in a docstring, and
nothing enforced it. `curl -X DELETE :8845/api/problems/<id>` deleted; MC's stop button fell through
to a bare stop when the impact fetch failed; learnhub had no deletion read at all. For an agent that
is exactly the wrong shape: the guard is prose the agent may not read, and the cheapest path is the
unguarded one. What is at stake is a chart node, a running app or a course with its study history
gone on the strength of a tool call that never saw what it was removing.

## Appetite

One evening across four repos. The pattern is one 60-line module copied verbatim; the work is threading `token` through five routes and their UIs.

## Plan

The impact read issues a token and remembers `(kind, target, digest-of-impact, expiry)`; the
destructive route takes `token` as a query parameter and refuses — naming the GET to make — when it
is missing, unknown, expired, issued for another target, or when the impact has changed since. Single
use; ten minutes; in-process only (a restart forgets every token, the safe direction).

Routes: shipyard `DELETE /api/problems/{pid}` ↔ `GET …/deletion`, `DELETE …/anchor` ↔ `GET …/impact`;
mission-control `POST /api/apps/{id}/stop` ↔ `GET …/impact`, `POST /api/ollama/delete` ↔ new
`GET /api/ollama/delete-impact`; learnhub `DELETE /api/document` ↔ new `GET /api/document/deletion`.
helm's Thaw dialog reads shipyard's impact through a new proxy and forwards the token (helm v1.8.1).

**Non-goals.** No shared package across tiers (the module is copied; libraries never learn about
surfaces). No persistence of tokens. No token on non-destructive writes. No UI for "why was I
refused" beyond passing the sentence through.

## Exit criteria

1. A bare `DELETE` on a scratch problem returns 422 whose detail names `GET /api/problems/{pid}/deletion`; the problem is still there.
2. The same `DELETE` with the token the read returned succeeds; the token cannot be reused.
3. Thaw behaves the same way against `GET …/impact`.
4. A token issued before the impact changed (a child added under the parent) is refused with "has changed".
5. The existing suite still passes with its deletes routed through the read.

## Build

- `backend/app/tokens.py` — `issue(kind, target, payload)`, `check(kind, target, token, payload, read)`; the digest is sha256 of the sorted-JSON impact, 16 hex chars.
- `main.py`: `api_problem_deletion` and `api_problem_impact` append `token`; `api_delete_problem(pid, cascade, token)` and thaw recompute the impact and call `tokens.check` before touching anything.
- `goals.jsx` passes `confirming.token`; `problem.jsx` passes `impact.token` to thaw. Both already fetched the read for the confirm dialog, so the UI change is one argument.
- Existing tests (`test_goals`, `test_chart`, `test_board`) gained an `rm()` helper that deletes through the read — 12 tests went red when the gate landed, which is the planted violation the rule owes.
- **Decision:** query parameter, not body — no DELETE in the codebase carries a body and the fleet MCP's generator already renders `?token=`.
- **Decision:** the impact is recomputed at write time and compared by digest, so the token proves the *current* consequences were read, not some earlier ones.

## Test

`backend/.venv/bin/python -m pytest tests -q` → **461 passed, 3 skipped** (6 new in `test_tokens.py`: bare refusal naming the read, single use, foreign target, changed impact, thaw, expiry).

Live, against the agentics worktree served on :8847 over a copy of the real DB (2026-09-05):

```
$ curl -X DELETE :8847/api/problems/6688888f5016
422 {"detail":"refused: read GET /api/problems/6688888f5016/deletion first and pass its token — the impact is what you are agreeing to"}
$ curl :8847/api/problems/6688888f5016/deletion   → token=<redacted-token>
$ curl -X DELETE ":8847/api/problems/6688888f5016?token=<redacted-token>"
200                      $ curl :8847/api/chart/6688888f5016 → 404
$ curl -X DELETE :8847/api/problems/2f541b790bf8/anchor
{"detail":"refused: read GET /api/problems/2f541b790bf8/impact first and pass its token — …"}
$ curl -X DELETE ":8847/api/problems/2f541b790bf8/anchor?token=<from impact>"   → 200
```

Both scratch problems were created and removed in the same run; the copy DB holds nothing of the live chart's history.

Sibling repos: mission-control v0.3.0 (`tests/test_tokens.py`, bare `POST /api/apps/{id}/stop` → 422 against the real registry before any process is touched), learnhub-core v0.22.0 (`test_deletion_token.py` + a Postgres round-trip in `test_delete_pg.py` proving the read removes nothing), helm v1.8.1 (`test_decisions_impact.py`: the proxy forwards `?token=`).

## Review

- The gate landed by breaking 12 green tests, which is the right order: the suite had been asserting that a bare delete works.
- Tokens live in one process. Two uvicorn workers would break this; shipyard runs one, and that is now a constraint worth an ADR if it ever changes.
- MC's stop button used to *fall through* to a bare stop when the impact read failed. With the token that path is gone: a failed read is a refusal with its reason. That was the most dangerous line in the fleet and nobody had written it down.
- Still open after this cycle: the live shipyard on :8845 runs `dev`, not `agentics`; the merge waits on the other session's uncommitted `_task_write` removal. Until then helm's Thaw dialog receives no `token` field from :8845 and thaws as before.
