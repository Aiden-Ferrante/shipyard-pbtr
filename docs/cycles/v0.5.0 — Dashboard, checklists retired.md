# v0.5.0 — Dashboard, checklists retired

Light plan (sub-cycle) under [[0.) Development Protocol 1.0]] · super-cycle: [[0.) Road to 1.0]]
Opened 2026-08-05

## Problem

Two halves of the same thing.

**The checklists have to go.** Floor / Run / See / Decide were called "not useful, cluttered" —
they measure conformance to a standard, and conformance was never the point. `standards.yaml`
is the one piece of logic shipyard genuinely owns, and [[0.) Road to 1.0]] scheduled its deletion
here.

**What replaces them is the variant-C dashboard**: open a project and see the open work *nested
underneath the problem it serves*, plus — the part that earns the layout — a **serves no
waypoint** section for work that serves nothing on the chart. A flat task list makes all work
look equally justified; nesting makes orphans visible.

## Appetite

**One day.**

## Decision — how work attaches to a problem

> [!important] A Backlog label, matched to the problem's title. Not a new store.
> A task must say which problem it serves, and that fact belongs **in the task**, not in
> shipyard — same reasoning that kept group membership in `PROJECT.yaml`.
>
> So: a task carries a **label** whose slug matches a problem's title slug (`habit` → *Habit*).
> Shipyard resolves the match at read time and owns nothing. Backlog.md already has `--labels`,
> so the cost is one flag per task and zero new machinery.
>
> Consequence to accept: **unlabelled work all lands in the orphan bin.** That is the honest
> default — an unlabelled task genuinely has no stated reason — but it means the section will
> look alarming until labelling catches up. Better than inventing an attachment.

## In scope

- Read `backlog/tasks/*.md` from a project's repo: id, title, status, labels, priority, type.
- Resolve tasks to chart problems by label ↔ title slug, anywhere in that project's subtree.
- `GET /api/projects/{id}/work` — problems with their nested tasks, plus orphans.
- Dashboard UI replacing the checklist tab.
- **Delete the checklists**: `standards.yaml`, `derive_checks`, the check routes, `/api/standards`,
  the `standards` health check, and the checklist UI.

## Out of scope — pruned

Writing labels from shipyard (v0.6.0) · task detail views · creating or closing tasks ·
non-Backlog task sources · the drift-inbox attach action.

## Guardrails

- **A repo with no `backlog/` is normal, not an error.** Most of the fleet has none.
- **Never invent an attachment.** If a label doesn't match, the task is an orphan and says so.
- **Deleting the checklists must not delete their data.** The `checks` table stays on disk
  untouched; only the code paths go. Reversing this decision should cost a revert, not a loss.
- No scoring, no completion percentages.

## Commit ladder

1. Backlog reader — parse task files, tolerate a missing `backlog/` — tests
2. Label → problem resolution, orphans included — tests
3. `GET /api/projects/{id}/work`
4. Dashboard UI, nested + orphan section
5. Retire the checklists: `standards.yaml`, derived checks, routes, health check, UI
6. CHANGELOG + tag

## Definition of done

- Learn Hub's dashboard shows its real open tasks nested under real problems, with at least one
  genuine orphan visible.
- No reference to `standards.yaml` remains anywhere in the codebase, and `/health` still returns
  `ok` with a coherent set of checks.
- The `checks` table still exists on disk with its rows.
- `make test` green, observed output shown.

## Retro — 2026-08-05, cut same day

**Definition of done — all met.**

- Learn Hub's dashboard, on real data after labelling: **Habit → 2 tasks, Engagement → 6**, and
  **2 serving no waypoint** (`TASK-27`, `TASK-7`).
- No reference to `standards.yaml` remains; `/health` returns `ok` with `db`, `code_root`, `mc`.
- The `checks` table is still on disk with its rows.
- 63 tests green, no console errors.

**The finding the layout produced immediately.** Effort is concentrated on the lens with the
*least* evidence. Engagement holds six of the ten open tasks and its waypoint ("I open it on a
day nothing is due") isn't instrumented at all; Habit — named the weakest link, and the one
gating whether any other lens can be measured — holds two. That's exactly the misallocation the
mock predicted, and it was invisible in a flat task list.

And `TASK-27` showing as an orphan is **correct, not a gap**: it serves the `<personal goal>`
bearing, which sits above the project rather than under it. Drift here means "the chart doesn't
reach that far", which is true.

**What bit.**

1. **A regex deletion ate two innocent functions.** Stripping the derived-checks block also
   removed `git_activity` and `git_last_activity`, which happened to live in the same region.
   The suite caught it immediately. Lesson: bulk-delete by regex, then *read the diff* — don't
   trust the pattern.
2. **I committed shipyard's work into learnhub-core and tagged it `v0.5.0`.** A `cd` from the
   labelling step persisted. Caught because the tag list came back reading `v0.14.0` — the wrong
   repo's history. Nothing was pushed, so: tag deleted, commit amended to a message about the
   labels (which were legitimately learnhub's), then committed properly in shipyard. **Rule for
   next time: never run `git commit` without an absolute `cd` in the same command.**

**Appetite.** One day budgeted, finished same day. Third cycle in a row.

**Carried forward.** Labels have to be applied by hand — writing them from shipyard is v0.6.0.
The orphan section can show but not resolve. Unlabelled work in other repos will all read as
drift until labelled, which is honest but will look alarming.
