# v0.6.0 — Write-back

Light plan (sub-cycle) under [[0.) Development Protocol 1.0]] · super-cycle: [[0.) Road to 1.0]]
Opened 2026-08-05

## Problem

v0.5.0 made unjustified work **visible** but not **fixable**. The "serves no waypoint" section
shows orphans and then leaves you to go open a terminal, remember the label convention, and type
it yourself — which is exactly the kind of friction that turns a good surface into one you stop
opening.

Shipyard's one-liner says it *"reads and writes"* the tools that hold the truth. v0.4.0 made that
half-true by writing `PROJECT.yaml`. This closes it for work.

## Appetite

**One day.**

## Decision — obey the target repo's rules, not just shipyard's

> [!important] Go through the `backlog` CLI. Do not edit task files.
> learnhub's `CLAUDE.md` states it directly: *"Do not edit Backlog task … markdown files
> directly. Use the `backlog` CLI so metadata, relationships, and history stay consistent."*
>
> That rule belongs to that repo, and shipyard is a guest in it. So the write-back **shells out
> to `backlog task edit <id> --add-label <x>`** rather than doing the surgical frontmatter edit
> that worked for `PROJECT.yaml`. Different repo, different owner, different contract.
>
> This is the general principle worth keeping: **when shipyard writes into a repo, it follows
> that repo's conventions.** A front end over other people's tools does not get to impose its
> own file format on them.

**Reachability note:** `backlog` lives in nvm's bin, which shipyard only sees because the
Mission Control systemd unit got an explicit `PATH` this morning. Worth a health check — a
write-back that silently can't run is worse than one that isn't offered.

## In scope

- Adapter around the `backlog` CLI: add / remove a label on a task, per repo.
- `POST` / `DELETE /api/projects/{pid}/tasks/{tid}/problem` — attach and detach.
- Dashboard: attach control on each orphan row, detach on each nested row.
- **Visible failure** when the CLI is missing, not a silent no-op.

## Out of scope — pruned

Creating or closing tasks · editing task titles or bodies · writing to the vault · non-Backlog
work sources · bulk attach · the drift-inbox attach action (that one is chart-internal, not
write-back).

## Guardrails

- **Never edit a Backlog file directly.** The CLI is the contract.
- **A repo without `backlog/` offers no attach control at all** — don't invite an action that
  cannot work.
- **Every write is one task, one label.** No bulk operations that are hard to undo.
- **Failures surface in the UI** with the CLI's own message; shipyard does not swallow them.

## Commit ladder

1. CLI adapter with a missing-binary path — tests
2. Attach / detach endpoints — tests
3. Dashboard attach + detach controls
4. Verified against a real learnhub task, reading the file afterwards
5. CHANGELOG + tag

## Definition of done

- An orphan attached **from the UI**, and the task file on disk carries the new label — confirmed
  by reading the file, and by `backlog task view` agreeing.
- Detach works and the task returns to the orphan section.
- With the CLI unavailable, the UI shows a real error rather than appearing to succeed.
- `make test` green, observed output shown.

## Retro — 2026-08-05, cut same day

**Definition of done — all met.**

- `TASK-7` attached to *Quality* **from the UI**: orphans 2 → 1, label on disk, `backlog task
  view` agreeing.
- Detach returned it to the orphan section and labels round-tripped **exactly** — the only
  residual was the CLI's own `updated_date` stamp, which is correct behaviour and was reverted
  since it came from verification rather than real work.
- Missing-CLI and no-`backlog/` paths both raise visible errors, covered by tests.
- 67 tests green.

**The decision that generalised.** v0.4.0 wrote `PROJECT.yaml` with a surgical line edit, and
the obvious move here was to do the same to task frontmatter. That would have been wrong:
Backlog.md repos state their own rule in `CLAUDE.md`. So the principle is now proven on two
different file types — **when shipyard writes into a repo, it follows that repo's conventions,
not its own.** The proof it mattered: the CLI stamped `updated_date` unprompted, which a
hand-rolled frontmatter edit would have silently skipped, and that drift would only have
surfaced much later as "why does Backlog think this task was never touched".

**A dependency worth noticing.** The whole cycle only works because `backlog` is on the PATH
shipyard inherits — which is true *only* because the Mission Control systemd unit got an
explicit `PATH` this morning. The first fix of the day turned out to be load-bearing for the
last feature of the day.

**No new bugs**, second cycle running. The `cd` discipline from v0.5.0's mistake held: every
git command in this cycle used an explicit `-C <abs path>`.

**Appetite.** One day budgeted, finished same day.

**Carried forward.** One task attaches to one problem (first match wins). No bulk attach. The
drift inbox still shows without resolving — only the dashboard can act.
